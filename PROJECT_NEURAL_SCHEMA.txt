1. PROJECT IDENTITY
================================================================================
Name ................. TrustShield (repo folder "TrustShield"; hosted URL slug is misspelled "trust-sheild")
One line ............. Real-time phishing prevention for phone users plus a forensic investigation portal for email.
Purpose .............. Stop people from opening phishing links BEFORE they open them (intercept links in
                       notifications), and give security teams a sealed, court-style forensic record of phishing emails.
Problem solved ....... Phishing links arrive via SMS/WhatsApp/email; users only learn they were scams after clicking.
Target users ......... (a) Consumers on Android (WhatsApp/SMS scams), (b) organisations / IT teams (browser extension +
                       email analysis), (c) forensic investigators (case IDs, evidence hashing, PDF dossiers, route maps).
Target environment ... Android 10+ (minSdk 29), web browsers (Chrome extension MV3, SOC web portal), Python backend.
Project owner context  Year-long personal project of the developer, intended also as placement project; being presented
                       at HACKERING 2.0 Round 2 (RVITM Bengaluru, 8-10 Oct 2026, 36-hour offline hackathon, "Open
                       Innovation" track = build/implement the idea presented in the previous round).

CURRENT STATUS (honest)
  - Android app (Kotlin, XML views): working notification-based link interception with 3-tier checking. REAL.
  - Backend pipelines (link + email forensics): working, hardened this session (auth, sealing, SSRF guard). REAL.
  - ML classifier: CODE COMPLETE (collector, trainers, runtime, integration, tests) but NO TRAINED MODEL FILE EXISTS YET.
    Until the developer runs training, the link verdict comes from rules only.
  - "Link Gate" (intercept the tap, scan, then open the browser): PLANNED, NOT IMPLEMENTED. No http/https intent filter exists.
  - Consumer portal / Organization console: PLANNED. Only the original forensic "SOC portal" exists (frontend/).
  - Play Store publication: PLANNED, not started.

IMPLEMENTED vs CLAIMED (README/pitch claims versus code)
  Claim: "ML classification model" ............ At the time of this document: NOT TRAINED. Legacy RandomForest (9 hand-typed
                                                rows) exists but is never called. New LightGBM stage is code only.
  Claim: "Sandbox analysis" .................... On Render: NO real browser. A plain HTTP fetch + HTML parse (no JavaScript).
                                                Real headless Chromium only runs where Chrome exists (local machine / the new Docker image).
  Claim: "VirusTotal API final layer" .......... REAL but conditional: needs VIRUSTOTAL_API_KEY; free tier 4 req/min, 500/day.
  Claim: "Phishing domain DB (Firebase)" ....... REAL on Android side (Firebase Realtime DB node "phishing_domains", cached locally).
  Claim: "Tamper-evident sealed evidence" ...... REAL after this session (HMAC-SHA256 seal re-verified on every read).
                                                Before this session it was NOT real (see section 14).
  Claim: "Court admissibility / BSA 2023 compliance" in older UI strings: NOT a technical guarantee; legal claim is unverified.

Core value proposition: detect and block phishing before the click, with explainable evidence.
Main use cases: (1) WhatsApp/SMS link arrives -> notification scanned -> alert. (2) Analyst uploads .eml -> case, route map,
                SPF/DKIM/DMARC audit, PDF dossier. (3) Webmail -> Chrome extension -> same analysis. (4) Manual link scan in app.
Hackathon angle: "zero-click" prevention + forensic trail; planned story = app catches it, portal proves it.

5. APPLICATION FLOW
================================================================================
5.1 FIRST RUN (Android)
  1. MainActivity (activities/MainActivity.kt) routes: user_id + is_logged_in + auth token present -> Home, else Login.
  2. Registration: POST /api/auth/register (name, last_name, email, phone_number, 4-8 digit PIN) -> user created; user returns to Login.
  3. Login: POST /api/auth/login -> {id,name,email,phone_number,token}. App saves user fields + token (SharedPreferences, AuthStore).
  4. HomeActivity checks Notification Listener access; if missing -> PermissionActivity (guides user; README explains sideload
     "Allow restricted settings" step). Asks POST_NOTIFICATIONS.
5.2 REAL-TIME LINK INTERCEPTION (core feature)
  1. Android delivers a notification to NotificationListener (service bound with notification-listener permission).
  2. LinkExtractor/UrlNormalizer pull URLs from notification text (and URLSpans in text lines).
  3. LinkAnalyzer Tier 1 (on device, instant): Official Domain Registry (VERIFIED_OFFICIAL -> SAFE, BRAND_ABUSE -> DANGEROUS),
     legacy trusted whitelist -> SAFE, rule checks (IP host, typosquatting via Levenshtein-style similarity, homograph, long URL,
     many hyphens, shorteners, phishing keywords, subdomain flooding, odd port). Unknown domain => SUSPICIOUS "needs Tier 3".
  4. If Tier 1 = DANGEROUS -> alert immediately + record to backend and stop.
  5. Tier 2: PhishingDomainCheckerFirebase.checkDomain(url): local cache of Firebase "phishing_domains" (DANGEROUS/SUSPICIOUS/SAFE).
  6. LinkScanRecorder POSTs /api/links/scan (user token; url, risk_level, reasons, verdict, source_app). The SERVER re-analyses:
     Tier-0 Postgres phishing DB match -> DANGEROUS; else runs the full server pipeline (section 7); stores the result in link_scans.
  7. If backend says DANGEROUS where device said otherwise, app raises an alert. SandboxChecker (/api/sandbox-check) is the explicit Tier 3 call.
  8. History: HomeActivity/DashboardActivity call GET /api/links/history/<user_id> (Bearer). LinkDetailActivity calls /api/links/explain.
5.3 EMAIL FORENSICS (portal)
  1. Analyst opens /portal, uploads .eml -> POST /api/forensics/analyze-eml (multipart).
  2. unified_email_pipeline.analyze_email_pipeline(eml_bytes) runs steps A-K (section 18).
  3. Server generates case_id "TSF-<16 hex>", seals (HMAC), INSERTs into forensic_cases, returns dossier + integrity block.
  4. Portal renders summary, headers, route map (Leaflet), IOC list, attack graph, evidence vault, timeline, report.
  5. Export: POST /api/forensics/export-pdf {case_id} -> PDF built from the stored sealed case.
  6. Verification: POST /api/forensics/verify-hash (case id or SHA-256) and /verify-file (re-hash an uploaded file).
5.4 CHROME EXTENSION
  1. content.js scrapes subject/sender/body/links from an open webmail page; popup.js sends POST /api/extension/analyze
     (tries local http://127.0.0.1:8000 then cloud https://trust-sheild.onrender.com).
  2. Backend synthesises a minimal RFC-5322 message (no real transport headers), runs the same email pipeline, stores a case.
  3. Extension opens /portal/ with the case id; portal loads GET /api/forensics/case/<id>.
5.5 DATA COLLECTION / TRAINING (developer workflow)  see section 7 and backend/ml/README.md.

7.1 LINK PIPELINE (backend/core_engine/link_threat_pipeline.py :: LinkThreatPipeline.analyze_url)
  INPUT: URL string (validated http/https, <=2048 chars, no whitespace) -> OUTPUT dict:
         {url, threat_score 0-100, verdict, analysis_complete, summary, telemetry{...}}.
  Stage 1  Heuristics (url_heuristics.parse_url_heuristics): raw-IP host (+45), '@' userinfo spoofing in the authority (+40),
           brand keyword inside subdomain while root differs (+50), >=3 stacked subdomains (+25), Shannon entropy of URL >4.5 (+20),
           URL length >120 (+10); score capped at 100; flags list. Brand list 28 keywords; short brands use token boundaries.
  Stage 2  Threat DB (threat_db.ThreatIntelDB.check_indicator): SQLite table malicious_indicators(indicator PK, source, date_added);
           keys tried: full URL, host, host without www, host+path, registered domain (registered domain skipped for brand
           domains and user-content hosts). Hit => score 100, instant block. Auto-sync from OpenPhish (and URLhaus if URLHAUS_AUTH_KEY)
           when empty or older than 12 h (background thread, ENABLE_THREAT_SYNC). Max ~1500 records per sync.
  Stage 2.5 Fast path + VirusTotal:
           BRAND_FAST_PATH_DOMAINS (64 brand registrable domains) => score 0, skip sandbox, "LEGITIMATE / CLEAN".
           USER_CONTENT_HOSTS (~100 entries: docs.google.com, sharepoint.com, github.io, blogspot.com, t.me, shorteners, and free hosts such as
           vercel.app, pages.dev, netlify.app, onrender.com ...) are NEVER auto-safe (exact host and any subdomain). The free-host group was
           added late in this session after a review found vercel.app/pages.dev were missing (their platform rank would have vouched for evil subdomains). VirusTotal v3 /domains/<d>: popularity rank <100k => risk 0, <500k => 10;
           >=2 malicious engines => risk 95 (vt_malicious). Cache: 24 h definitive / 5 min errors, SQLite backend/data/vt_cache.db;
           client limiter 4/min and 500/day; HTTP 429 never cached (60 s backoff). timeout 2 s.
  Stage 3  Sandbox (sandbox_engine.VirtualSandboxAnalyzer.analyze_link_in_sandbox):
           a) SSRF guard url_safety.assert_public_url (scheme http/https only, no credentials, resolve DNS, every address must be
              public/global; applied to the initial URL and each redirect hop in the HTTP path).
           b) Domain age via RDAP (rdap.org), 3 s timeout, cached; <14 d => risk 90, <30 d => 60; unknown => -1 (no signal).
           c) If Chrome available (not when env RENDER/DYNO/FORCE_CLOUD_SANDBOX set): Selenium headless Chromium with stealth,
              page_load_timeout 4 s, +0.5 s wait; extracts password inputs, forms and their action targets, hidden iframes,
              title/brand mismatch, brand impersonation; stores page HTML (<=400 KB) for ML features.
              Else/ on error: HTTP "Cloud DOM sandbox": manual redirect following (<=5 hops, each re-validated), 5 s budget,
              1.5 MB body cap, HTML parse (no JavaScript executed). JS-built login forms are INVISIBLE in this mode.
           d) Detections: password field on non-brand domain, form action to another registered domain, exfiltration hosts
              (api.telegram.org, discord.com, discordapp.com, formspree.io, formcarry.com, emailjs.com, webtooid.com, pastebin.com, raw IPs,
              https page posting to http), hidden iframes (<=1px or display:none), brand impersonation vs an 11-brand list
              (word-boundary keyword match in title/meta/body), title mismatch (real brand names only, requires credential form).
           e) sandbox_threat_score additive (password+risk 45, external form 40, exfiltration 55, brand impersonation 50,
              new domain 35, title mismatch 30, redirect 20, hidden iframe 25; capped 100). Unreachable => 40.
  Stage 4  ML (ml/model_runtime.ModelRuntime.score)  -- see 7.2. Returns None if no artifacts => rules continue.
  Stage 5  Fusion (final_decision_engine.FinalDecisionEngine.evaluate):
           Hard overrides (first match wins): known DB match 100; exfiltration+password 100; brand impersonation+password 100;
           brand impersonation+external form 95; domain<14d + password 90; VT>=90 + password 95; VT>=90 alone 90 (VT_MALICIOUS_FLOOR).
           Else weighted sum: sandbox 0.30, heuristic 0.15, nlp 0.20 (0 for links), domain-age 0.15, VT 0.10 (default VT=35),
           typosquat flag 0.10 (75 if the heuristic "brand in subdomain" fired) + boosters (brand imp +45, exfil +45, external form +35,
           password-with-risk +30, title mismatch +25, entropy +15, hidden iframe +20).
           If ML present and no hard override: threat_score := ml.score (monotonic map of probability; see 7.2).
           Floors (raise only): raw-IP host with credential-style path or non-standard port 60; brand-in-subdomain 70; '@' spoof 65.
           Incomplete analysis (sandbox unreachable or blocked): analysis_complete=False; score floored to 50 only if a risk signal exists
           (domain<30d, heuristic flags, typosquat flag).
           Verdict: >=80 "CRITICAL FRAUD / PHISHING", >=50 "SUSPICIOUS", else "LEGITIMATE / CLEAN".
           App mapping (app.py to_client_verdict): CRITICAL->DANGEROUS, SUSPICIOUS->SUSPICIOUS, else SAFE.
           Explanation text: deterministic 3-bullet template (Threat Summary / Key Forensic Evidence / Recommended Action), plus an ML line.
  Fallbacks: no VT key -> VT stage skipped (default 35); VT 429 -> neutral; sandbox failure -> HTTP fallback -> unreachable score 40;
             ML missing/error -> rules; DB errors -> app keeps client verdict as hint with tier "CLIENT_ONLY".

7.2 NEW ML SUBSYSTEM (backend/ml/)  -- STATUS: UNTRAINED
  Models (two, both LightGBM LGBMClassifier via scikit-learn API, class_weight="balanced", early stopping on val logloss,
          up to 3000 trees, lr 0.05 (0.03 if <20k rows), leaves 63 (15 small), subsample .8, colsample .8, lambda 1, seed 7):
   (1) LEXICAL model  artifact: core_engine/trained_models/lexical_model.joblib (+ .json report, lexical_train_urls.npy)
       Input: 28 HOST-LEVEL features from ml/features.LEXICAL_HOST_FEATURES (host length, hyphens, digits, entropy, subdomain count/length,
              TLD id/abused TLD, scam keywords in host, brand-in-unrelated-domain (58-brand map), free-hosting flag, shortener, token stats, punycode, IP host...).
              Path/query/length/scheme features are DELIBERATELY excluded (dataset-shortcut risk: benign sets are bare home pages).
              A leading "www." is stripped before features.
       Training data (ml/datasets.py, all public, label 1 = malicious phishing OR malware): PhishTank online-valid CSV (~70k),
              URLhaus csv_online (~27k), Phishing.Database ACTIVE (~789k; capped 70k), OpenPhish (~300), PhiUSIIL phishing (~100k; capped 70k);
              benign: PhiUSIIL legitimate (~135k), Tranco top-1M home pages (90k sample), plus benign deep links from collected pages.
              Per-site cap 6 URLs per class; URLs/sites present in collected pages.jsonl are held out.
       Split: deterministic by site (md5 of group key): 70/15/15 train/val/test, no site on two sides.
       Calibration: isotonic regression on validation. Thresholds: t_high = lowest probability whose DANGEROUS precision >= 99% at an assumed
              5% real-world malicious prevalence (benign reweighted); t_low = highest probability below which <=2% of malicious fall.
              Between t_low and t_high => SUSPICIOUS.
   (2) PAGE model  artifact: page_model.joblib  (FINAL ML stage)
       Input: 28 host features + 44 page features (ml/features.page_features: forms, password inputs, form action external/empty/POST,
              scripts (inline/external), links (external ratio, null links), iframes (hidden), images, meta refresh, JS redirect,
              title (length, login words, brand, brand mismatch), body text length, login wording, external favicon, right-click blocked,
              obfuscation calls (eval/atob/unescape/fromCharCode/document.write), SPA-shell flag, redirects, host change, domain age,
              new-domain flag, sandbox flags, copyright-brand mismatch, unique external domains) + lexical probability (out-of-sample).
              Excluded shortcut features: is_https, ends_with_slash, final_is_https. Unreachable pages are NOT used for training;
              they fall back to the lexical model at runtime.
       Training data: backend/ml/data/pages.jsonl produced by ml/collect_dataset.py: visits URLs in real Chromium INSIDE DOCKER, stores
              sandbox features + zlib/base64 HTML (<=250 KB). Malicious mix: PhishTank 40%, Phishing.Database 25%, OpenPhish 20%, URLhaus 15%;
              benign: Tranco stratified over rank buckets 1-1k, 1k-10k, 10k-100k, 100k-1M plus up to N same-site deep links.
              Measured collection speed: ~1,000 pages/hour with 4 browsers.
  Runtime (ml/model_runtime.py): env ENABLE_ML (default true), TRUSTSHIELD_ML_DIR override. If page fetched + page model + lexical model:
       page model; else lexical model; else None. Output: probability, band (SAFE if p<=t_low, DANGEROUS if p>=t_high, else SUSPICIOUS),
       score (piecewise-linear so that bands align with the 50/80 verdict cut-offs: <=t_low -> 0..49, between -> 50..79.9, >=t_high -> 80..100),
       model name/version, lexical probability, top positive SHAP-style contributions (LightGBM pred_contrib) mapped to readable labels.
  Evaluation: ml/evaluate_live.py pulls the freshest OpenPhish/PhishTank links and unseen Tranco sites (excluding training URLs/sites), runs the full
       pipeline (threat DB and VirusTotal OFF by default) and prints band percentages, misses, false alarms, latency.
  Dry-run evidence from development (NOT final metrics): 8,000-row lexical dry run gave ROC-AUC ~0.86; 303-page toy page model gave AUC 0.88
       versus 0.74 for lexical alone on 66 test pages (22 malicious). Statistically weak; real numbers require the full run.
  Earlier live probe (rules only, empty threat DB, no VirusTotal, HTTP sandbox): 24 live OpenPhish URLs -> only 2 flagged;
       12 legitimate sites -> 2 falsely flagged (mozilla.org, news.ycombinator.com). This is the baseline the ML work targets.
  Known ML risks: dataset artefacts (path/https/www), cloaking phishing pages, label noise (URLhaus includes malware), covariate shift between
       feed pages and real traffic, small page set when only a few thousand pages are collected.

15. SECURITY
================================================================================
Authentication: phone + PIN (4-8 digits, bcrypt cost default), signed bearer token (itsdangerous, 30 days, no revocation/refresh). Token stored in app-private
  SharedPreferences (not EncryptedSharedPreferences). allowBackup=false.
Authorization: ownership enforced for history, scans, explain, case evidence, case list. Forensic case READ by id is a capability URL (unguessable 64-bit id, rate-limited).
  Graph/campaign endpoints require login but data is global across users (cross-tenant leakage) - documented limitation.
Input validation: URL normaliser, email/phone/PIN validators, header-injection stripping for extension-submitted fields, upload cap 10 MB, list caps.
SQL injection: all queries parameterised; one f-string SQL fragment uses a fixed two-value order clause.
SSRF: url_safety guard blocks private/loopback/link-local/multicast/non-http. Residual: DNS-rebinding window (resolve then fetch are separate); Selenium path
  cannot validate redirects/JS navigations after the first load (isolate Chromium in the container/network).
XSS: portal builds HTML from API data in JS (innerHTML patterns likely present; full audit NOT performed). PDF text is escaped (reportlab Paragraph markup).
CORS: restricted origin list + extension; no cookies are used (bearer tokens), so CSRF risk is low.
Secrets: .env ignored by git; Green-API token remains in git history (rotate); no secret defaults remain in code; production fails fast without SECRET_KEY/DB vars.
File upload: .eml parsed in memory; attachments are analysed, never executed or stored; HTML parsing hardened with lxml.
Prompt injection / AI security: no LLM in the active path; BEC rules read untrusted text only for regex matching.
Data exposure: notification text stays on device; only extracted URLs (plus source app package name) are sent. Server logs include URLs (PII-adjacent).
Operational: sandbox opens attacker-controlled pages - run in Docker with no host mounts besides ml/data; data collection uses --security-opt no-new-privileges.
Admin: X-Admin-Key header, constant-time compare; disabled when unset.

  - Sandbox page load is the slowest step: HTTP fallback up to ~5 s; Selenium ~4-8 s; RDAP up to 3 s (cached). Concurrency capped (4, Docker 2) with 20 s wait.

17. ERROR HANDLING
================================================================================
  Backend: handlers wrapped in try/except returning server_error(): logs full exception with a 12-char reference id, returns a generic message. Validation errors 400,
    auth 401, forbidden 403, lockout/rate-limit 429 (+Retry-After), busy 503. DB writes for forensic cases RAISE on failure (no id is handed out without durable storage).
  Pipelines: each forensic module's failure is recorded in analysis_errors and sets analysis_complete=False (summary says "analysis incomplete", never silently clean).
    DNS failures are "indeterminate", not pass/fail. Link pipeline: sandbox error -> HTTP fallback -> unreachable (score 40, analysis_complete False).
  AI/ML: any ML error returns None and the rules verdict stands. Model/feature-version mismatch disables the artifact with a warning.
  Android: network errors toast/log; Retrofit retry interceptor (3 tries, 8 s wait on 502/503 for Render cold starts); 401 clears the stored token (user returns to login on next screen);
    Tier-3 failure returns verdict UNKNOWN (device verdict stands).
  Logging: stdout via logging + many print statements; HTTP access logs from gunicorn. No central log aggregation, no metrics.

18. IMPORTANT ALGORITHMS / BUSINESS LOGIC
================================================================================
  Shannon entropy (url_heuristics.calculate_shannon_entropy; ml/features.shannon_entropy): H=-sum p log2 p; URL entropy >4.5 flags obfuscation/DGA.
  Brand-in-subdomain: brand keyword appears in a subdomain label while the registrable domain is not that brand (heuristics + ml BRAND_DOMAINS mismatch).
  SSRF host validation (url_safety): resolve all A/AAAA; reject any non-global address; handle IPv4-mapped IPv6; reject credentials and non-http schemes.
  SPF evaluator (email_forensics.evaluate_spf): recursive mechanism evaluation with qualifiers, CIDR, macros(basic), 10 DNS lookup limit, depth cap, 6 s budget -> pass/fail/softfail/neutral/temperror/permerror.
  DKIM alignment: each DKIM-Signature verified separately; aligned if verified d= domain is organisationally aligned with From (relaxed; strict if adkim=s).
  DMARC: record at From domain (fallback organisational domain); pass if aligned SPF or aligned DKIM; indeterminate on DNS error.
  Connecting IP vs origin IP: topmost Received with a public IP = connecting_ip (used for SPF); bottom-most public IP = claimed origin (geolocation/attribution; forgeable).
  Email threat score (unified_email_pipeline Step D): base = max link score if >=70 else half of it; +30 if SPF and DMARC fail (or +15 DMARC only);
    +35 Reply-To mismatch; +20 anonymised origin (Tor/proxy/hosting); then +BEC (<=20), +WHOIS (<=20), +attachments (<=25); verdict >=80 critical, >=50 suspicious.
  Threat attribution (classify_threat_attribution): maps auth/origin/metadata/link score into actor types (e.g. spoofed identity, anonymised infrastructure).
  Campaign fingerprint (campaign_manager): sha256 of origin IP (skipped for shared mail providers) + sender domain + first malicious URL registrable domain;
    uuid4 ids; ingest only score >=40; LRU cap.
  Graph correlation: nodes DOMAIN/IP/ASN/URL/EMAIL with edges; D3-format export; shared-infrastructure queries.
  Evidence sealing (evidence_seal.py): signature = HMAC-SHA256(key, case_id \n evidence_hash \n sha256(canonical_json(dossier)) \n sealed_at).
  VT rate limiter + TTL cache; threshold selection (ml/trainlib.choose_thresholds, prevalence-weighted precision); ML score mapping (ml_to_score).
  Grouped deterministic split (md5 of site key % 100). Isotonic calibration. Per-site caps to stop one hosting platform dominating the data.

21. JUDGE-QUESTION KNOWLEDGE  (answers reflect the actual implementation)
================================================================================
Q: Why intercept notifications instead of a browser/DNS filter?
A: Zero-click: the link is judged when it arrives, before any app opens it, and works for any messaging app that shows the URL. Limit: apps that hide URLs, and
   no blocking at tap time yet (planned Link Gate). A DNS/VPN filter would cover in-app browsers but cannot afford a multi-second sandbox per request.
Q: How does detection work?
A: Layered: URL heuristics, known-threat feeds (OpenPhish/URLhaus synced), VirusTotal domain reputation/popularity, a sandbox that loads the page and inspects forms/targets/brands,
   then a fusion engine (hard security rules + weighted score). A LightGBM classifier is implemented as the final stage and will be trained on public feeds plus pages
   we fetched; until trained, the rules decide.
Q: What is the accuracy?
A: Not yet measured on a trained model. Baseline measurement of the rules-only pipeline on 24 live phishing URLs flagged 2 and falsely flagged 2 of 12 legitimate sites
   (small sample, no feeds, no VirusTotal, HTTP sandbox). We built ml/evaluate_live.py to report held-out numbers on fresh links.
Q: Is it really machine learning?
A: The ML stage is implemented (two gradient-boosted models, calibrated probabilities, honest grouped evaluation). We will state the metrics produced by the evaluation script.
   The older "meta classifier" was a 9-row demo model and is not used.
Q: How is the forensic evidence tamper-evident?
A: SHA-256 of the original uploaded bytes + HMAC-SHA256 seal over case id, hash, canonical dossier and timestamp with a server key; rows are insert-only; the seal is re-verified on every read
   and via verify-hash/verify-file. Limitation: symmetric key held by the server (not a third-party timestamp or a public-key signature).
Q: Scalability?
A: Currently one gunicorn worker, in-memory rate limits/graph, Postgres without pooling, concurrency-capped sandbox. Scaling path: stateless workers (move limits/graph to Redis/Postgres),
   job queue for sandbox, pooled connections, per-tenant data.
Q: Security of fetching attacker URLs?
A: SSRF guard on every hop, manual redirect handling, size/time caps, safe HTML parsing, Docker isolation for the browser. Residual: DNS rebinding and browser-side redirects.
Q: Privacy?
A: Notification text never leaves the device; the server receives only the extracted URL, source app package, and the user's token. History is per user.
Q: Cost?
A: Free tiers today (Render, Neon, VirusTotal free key). Real sandbox needs ~1 GB RAM always-on (about $5-10/month on Fly/Railway).
Q: Limitations?
A: Cloaked phishing, URLs hidden in message previews, sideload-only install, in-app browsers bypass any tap-time gate, free-tier quotas, no multi-tenant model, ML not trained yet.
Q: What is innovative?
A: Pre-click interception combined with a forensic-grade evidence chain in one product; layered pipeline with explicit "analysis incomplete" handling instead of silently reporting clean.
Q: Why Python/Flask, Kotlin, Postgres?
A: Developer familiarity and rapid delivery; Python has the DNS/DKIM/PDF/ML ecosystem; Android notification access requires native code; Postgres gives durable relational storage.
